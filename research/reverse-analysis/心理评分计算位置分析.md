**结论：已追踪的原生心理检测采用“服务器下发评分配置 → 本地按所选档位取分 → 将分值提交服务器”的流程。** 它不是在手机上把多个答案代入一个已发现的复杂公式，也不是每次拖动滑杆都等服务器重新算分。本地确实有选项映射、提交整理和阈值检查；人格模型与积累曲线的数据通过接口读取。

## 已确认的数据流

| 环节 | 代码行为 | 计算位置及含义 |
| --- | --- | --- |
| 获取检测项目 | `SelfTestActivity.getMpTestList()` 发起 GET，请求参数包含心理项目 ID、检测类型、用户身份及心理类别 | 检测数据从接口取得，配置随身份、类型或项目而变化具备实现条件；具体差异值尚未采样 |
| 解析响应 | HTTP 成功回调从 `DataListModel<HeartEntity>` 取数据，交给 `DetectionLayout.prepareData()` | 响应组织成可检测项目；准备方法主要筛选项目，没有在此生成分值表 |
| 展示评分 | `SelfDetectionView.addNumView()` 读取 `entity.getScoreInfo()`，按数组长度设置滑杆档位 | 档位数量由数据驱动，不能将当前账号看到的 0–12 硬编码成全体项目规则 |
| 选择档位 | 滑杆位置转为整数；非零位置取 `scoreInfo[i - 1]`，通过回调返回该选项对象 | 本地按选项表取值；零档进入重置分支，不直接证明它是一个可提交的零分选项 |
| 整理结果 | `onResultListener()` 读取选项的 `score`；`processScore()` 将 `level`、`score`、心理项目 ID 放入提交对象 | 已追踪的这段代码复制选项值，没有对多个答案加权求和 |
| 超标提示 | `isAlert()` 检查检测标准是否开启、所选分数是否超过 `mind_standard_score`，以及是否已选择强制提交 | 检查在本地发生，阈值由项目对象携带；不能凭此得出服务器没有校验 |
| 提交 | `setUserMpDetection()` 将提交对象列表序列化到 `detection_content`，通过 POST 发出，成功后清理提交缓存并推进流程 | 客户端已经持有明确分数再提交，服务器负责的额外处理仍未知 |
| 人格模型和曲线 | `PersonModelView.getData()`、`getCurve()` 分别请求模型数据与积累曲线 | 展示数据通过接口获得；不能仅由此判断服务器内部采用何种汇总公式 |

对应的接口动作常量已从 `Constant` 静态初始化代码确认：

| 动作 | 常量值 |
| --- | --- |
| 获取心理检测配置 | `getMpTestListNew` |
| 提交心理检测 | `setUserMpDetectionNew` |
| 获取人格模型心理数据 | `getMindPracticeAllNew` |
| 获取心理积累曲线 | `getMindAccumulateCurveNew` |

这些动作名来自安装包。后续已用正常读取协议取得 getMpTestListNew 和 getMindPracticeAllNew 的实际响应；提交接口没有调用。

## 对仿品实现的影响

**已验证的单项心理检测适合按配置驱动实现。** 需要的数据包括心理项、身份与检测类型、选项档位、每档分数和阶段说明、检测资格、标准分阈值及历史记录。本地负责交互、取值、校验和提交，不必先假设存在一个复杂的通用推算模型。

后续已经导出 26 个主项及 8 个子项，共 429 条选项，包含资格、标准分和说明；见 [实际配置及限制](等级与生命海洋规则分析.md)。其他身份、检测类型及历史汇总规则仍未采样。

以下事项仍未确认，不能写成原产品事实：

- 服务器是否信任客户端分值，还是会重新计算、校验、修正、合并历史或控制重复提交。
- 模型数据和曲线在服务器上如何汇总，是否涉及权重、衰减、周期或身份差异。
- 心理数据如何驱动身份升级、船只和生命海洋的变化。
- 应用内网页“初级正念禅修自检”的评分与诊断报告逻辑。本次结论针对原生心理检测路径，不能直接套用到该网页问卷。

本轮已回答“单项分数怎样产生、怎样提交、模型数据从哪里读取”；综合模型的完整计算规则仍属于未解问题。
